DOM-based XSS

DOM-based Cross-Site Scripting

The "it never even touched the server" vulnerability.

1. Intro

DOM-based XSS is different from reflected and stored XSS in one key way: the server is never involved in the vulnerable data flow at all. The entire bug lives in client-side JavaScript.

It happens when JavaScript already running on the page takes data from an attacker-controllable source — things like location.hash, location.search, document.referrer, window.name, or data read from storage — and passes it into a dangerous sink — things like innerHTML, document.write(), eval(), or setAttribute('href', ...) — without sanitizing it first.

Because the fragment (the part of a URL after #) is never sent to the server at all, this kind of payload can completely bypass server-side defenses like input validation or a WAF that only inspects the request — the vulnerable code path only ever exists inside the victim's browser.

Real-world impact: identical to reflected/stored XSS once triggered (cookie/session theft, account takeover, etc.) — only the delivery mechanism and the fact that it's invisible to server-side logging differ.

2. How it's performed (conceptually)

  1. Read the client-side JavaScript (it's always visible to anyone — "view source" / dev tools). Look for code that reads from a source like location.hash, location.search, document.URL, document.referrer, or window.name.
  2. Trace where that value goes. Does it get written into innerHTML/outerHTML? Passed to document.write()? Used inside eval() or a new Function(...)? Used to set an attribute like href, src, or an inline event handler?
  3. Craft a payload for that specific source → sink path. For a location.hash → innerHTML flow, an HTML payload works, e.g. #<img src=x onerror=alert(1)>.
  4. Deliver the URL to a victim. Since the payload lives entirely in the fragment, it works even against sites that heavily validate everything sent to the server — because this part of the URL is never sent there.

Defensively: treat every client-side source the same as you'd treat server input — never pass it to a dangerous sink unsanitized. Prefer textContent, use the browser's built-in encoding (e.g. element.setAttribute with validated values), and avoid eval/document.write entirely.

dom/index.html — relevant snippet 
// THIS IS INTENTIONALLY INSECURE CODE, FOR TRAINING ONLY
function renderFromHash() {
  const hash = decodeURIComponent(window.location.hash.slice(1)); // source
  const match = hash.match(/name=(.*)/);
  if (match) {
    const name = match[1];
    welcomeContent.innerHTML = '👋 Welcome, ' + name + '!';  // sink: innerHTML
  }
}
window.addEventListener('hashchange', renderFromHash);

The fix: use textContent instead of innerHTML, or HTML-escape name before inserting it into markup.
