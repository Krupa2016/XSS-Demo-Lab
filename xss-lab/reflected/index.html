Reflected XSS

Reflected Cross-Site Scripting

The classic "echoed search box" vulnerability.

1. Intro

Reflected XSS happens when a web application takes input from a request — most commonly a URL query string parameter, but it could also be a form field, header, or cookie — and immediately writes it back into the HTML response without properly encoding it first.

Because the payload is "reflected" straight back in the same request/response cycle, it's never stored anywhere. That means an attacker usually has to trick a victim into clicking a specially crafted link (e.g. in a phishing email or a forum post) that contains the malicious payload in the URL. When the victim's browser loads that link, their own browser executes the attacker's script in the context of the trusted site.

Real-world impact: session/cookie theft, keylogging, defacement, forced actions on the victim's behalf, credential phishing overlays, etc.

2. How it's performed (conceptually)

  1. Find an input that gets reflected. Search boxes, error messages ("No results for '...'"), "welcome back, [name]" banners, and form validation messages are classic spots. Try entering a unique marker string (e.g. zzz12345) and view-source the response to see where it lands.
  2. Check how it's reflected. Is it inside plain HTML text? Inside an HTML attribute (value="...")? Inside a <script> block? Each context needs a slightly different payload to "break out" of it.
  3. Craft a breakout payload. For plain HTML text context, something as simple as <script>alert(1)</script> or an event-handler trick like <img src=x onerror=alert(1)> is often enough.
  4. Confirm execution. If your JS runs (e.g. an alert box pops, or the page makes a request to a URL you control), the input is unsanitized.
  5. Weaponize the URL. Encode the payload into a query string, then get a victim to click it — e.g. via a shortened link, QR code, or a link embedded in a message.

Defensively: the fix is always output encoding — HTML-escape user input before writing it into HTML (or use safe DOM APIs like textContent instead of innerHTML), plus a strong Content-Security-Policy as defense in depth.
