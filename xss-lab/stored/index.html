Stored XSS

Stored (Persistent) Cross-Site Scripting

The "poisoned guestbook" vulnerability.

1. Intro

Stored XSS (also called persistent XSS) happens when user-supplied input is saved on the server — in a database, a file, a comment thread, a user profile field, etc. — and later rendered back into pages without sanitization, for every user who views that content.

This makes it more dangerous than reflected XSS: the attacker doesn't need to trick a specific victim into clicking a crafted link. They just submit the payload once (e.g. as a blog comment, product review, username, or support ticket), and every single visitor who later views that page automatically executes the attacker's script.

Real-world impact: mass session hijacking, worm-like self-propagating payloads (e.g. the 2005 Samy MySpace worm), admin panel takeover if an admin views the poisoned content, persistent defacement.

2. How it's performed (conceptually)

  1. Find a persistence point. Any feature that stores user text and later displays it to other users: comments, reviews, forum posts, display names, bios, support tickets, chat messages.
  2. Check how it's rendered later. Does the app re-encode it when displaying, or does it trust what was stored? Submit a harmless unique marker first and inspect the rendered page's source.
  3. Submit a payload instead of normal content. E.g. post a "comment" that is actually <script>...</script> or an <img onerror=...> tag.
  4. Wait for a victim to view it. Could be any visitor to that page, or specifically an admin/moderator who reviews submitted content (often a higher-value target since they may have elevated session privileges).
  5. Payload executes in the victim's browser, in the trusted origin's context — able to read cookies (if not HttpOnly), make authenticated requests, modify the DOM, etc.

Defensively: always HTML-encode stored content at render time (never trust that it was "already safe" when stored), use a strict Content-Security-Policy, and consider sanitizing/stripping dangerous HTML on input too as defense in depth.

// THIS IS INTENTIONALLY INSECURE CODE, FOR TRAINING ONLY
function renderComments() {
  const comments = JSON.parse(localStorage.getItem('xss_lab_comments') || '[]');
  commentsList.innerHTML = comments.map(c =>
    `<div class="comment-item">
       <div class="comment-meta">${c.name}</div>
       <div>${c.text}</div>   <!-- raw, unescaped -->
     </div>`
  ).join('');
}

The fix: HTML-escape c.name and c.text before building the markup (or build nodes with textContent instead of a template string fed to innerHTML).
